The optimization journey

mtwRequest's fanout‑500‑subs p50 dropped from 418.9 ms to 64.5 ms across six versions. Each version is a targeted change in the hot path.

Fanout 500 subs · p50 latency over versions

delta
−354.4 ms
  1. v1 282.3 ms

    Encode‑once. SharedEnvelope lazily caches the wire bytes for each wire format. Fanout to N subscribers now serializes the message exactly once.

  2. v2 130.7 ms

    Direct‑sink + ArcSwap. Publish delivers straight into each connection's writer queue — no central forwarder. Subscriber list becomes a lock‑free atomic snapshot.

  3. v3 169.0 ms

    ConnTarget cache. Each subscriber resolves its writer handle once at subscribe time. Zero DashMap lookups on the hot path. (Apparent regression was run‑to‑run noise.)

  4. v4 107.0 ms

    Write batching. Per‑connection writer does feed then one flush per burst. TCP syscalls drop by 10×.

  5. v5 64.5 ms

    Zero‑copy text path. Upgrade to tokio‑tungstenite 0.29 and wrap cached Bytes as Utf8Bytes via an unsafe zero‑copy cast. Goodbye to one heap allocation per delivery.

The headline isn't the 17 % median improvement — it's the 4.7× tighter p99 distribution. MsgPack's tail is predictable where JSON's isn't. §6

Method the honest part

Benchmarks lie by omission more often than by malice. Here are the conditions, so you can judge.

Topology
Same host. Publisher, subscribers, and server on one machine. Relative numbers only — don't extrapolate to distributed deployments.
Resource caps
Every competitor runs in Docker with cpus: 2.0 and mem_limit: 2g. mtwRequest runs natively at equivalent concurrency.
Histograms
HdrHistogram, 3 significant figures, 1 ns – 60 s range. Warm‑up phase excluded.
Payload
128 bytes, with a 16‑byte u128 nanosecond timestamp in the leading bytes. Subscribers compute now − sent on receive.
Isolation
The publisher never subscribes to the channel it publishes on — no self‑delivery is counted.
Code
